# 页面操作与反馈

当前实现保持原上传、项目列表、智能解读/制作/审查导航及详情分栏。业务动作在页面，dsh Agent仅展示。入口、实现范围与启动见 [README](../README.md)。

## 上传和智能解读

从原上传卡片选择或拖入一份原件，创建项目并上传到 `data/workspace/<task_id>/sources/`，进入同一项目详情。上传不自动发起模型或OCR。详情可补充来源文件，再点击「开始解读」。首次上传的招标文件默认成为主文件。原文上方现有选择框同时切换预览与当前解读主文件，切换及补充来源勾选立即保存到项目data中的sources.json，重新进入保持选择。新文件上传后保留当前选择，用户手动切换到更新版本；不另加主文件选择框。运行中暂停来源切换，来源选择变化会更新后续动作的依据版本。来源保存成功会使此前及保存期间发出的旧详情读取失效；来源保存与生成动作共用项目提交锁，版本检查和写入在同一次受保护的提交内完成，并发提交或过期版本返回冲突。

当前六栏：基本信息、投标要求、评分标准、格式要求、废标条款、补充说明。八件灵燕原生MD直接渲染；表格和公式保留。详情顶部复用原项目的浅蓝进度样式，六栏目分别显示文档产出进度；重新解读按本轮写入统计，旧结果不计入本轮。运行中同内容重新写入仍计为新产出。进度绑定最近一轮解读；执行结束后保存快照，后续制作动作和人工编辑不改变该轮进度，重新解读才开启新轮统计。文档中的具体未知项、冲突和缺项照常显示，不增加泛化确认提醒。栏目后续按实际讨论调整。

「查看依据」使用当前任务解析MD和真实文件名、行号就地展开，没有映射时提示无法定位；不编造PDF页码或图片坐标。「收起原文/查看原文」沿用详情分栏，制作和审查中使用原件预览弹窗。

## 阅读与编辑

react-markdown + remark-gfm渲染，关闭内嵌HTML。内部来源标识、来源登记和机器元信息不展示。业务字段编辑由Markdown AST取得可编辑文本片段，保存时写回原位置；隐藏字段和原始关联保留，不调用二次模型转格式。

目录阅读使用灵燕编号/折叠树，标题突出，概述次级显示。编辑时支持标题、增删、同级顺序、升降级与编号；保存前处理同册重复叶子和深度限制。不同册同名章节按册名定位到原生DOCX路径。跨册拖拽和新增/删除整册尚未实现。

## 制作和审查

制作页保留「目录与章节」「写作指引」「关键事实与承诺」。默认左侧40%目录树、右侧60%所选章节Word预览。目录生成只通过按钮弹窗发起，弹窗无通用输入框，只有目标篇幅（含不限）与编号。篇幅是整册规模参考，进入目录及写作指引的逐节篇幅分配，不承诺精确Word页数；编号统一用于目录展示和合册标题。指引/承诺的可选要求、单章修订要求各在对应动作弹窗中填写。

顶部「开始制作标书」自动复用当前有效规划，仅生成缺失规划；已就绪规划在制作中禁止重写。准备过期时显示招标来源、解读、目录/篇幅或指引变化，用户在对应页签核对、编辑并保存后继续。人工保存也必须通过文件契约校验，失败保留原文。缺具体值时同会话提问/续接。整本默认补写缺失及未完成章节；已有且依据变化的正文保留，由用户预览后选择「已核对，保留当前章」或「更新当前章」。三个页签仍可独立查看、编辑、生成。制作动作在未保存草稿或已有执行时禁用。“生成当前章”在缺失准备时仍可点击，自动补齐指引和承诺；具体缺值在同一会话问答后续写，只生成所选章并校验，不自动合册。进度按真实准备状态显示指引、承诺、等待具体答复及所选章名，停止后复用已完成准备。

章节状态根据实际Word文件与编写依据显示未生成、待完成、已生成、待更新、待核对。章节需实际写入并通过原工具校验才记为本次编写完成；只读检查旧正文不会更新其依据。机械「目录」页与目录容器不计入需编写章节。标题/册名变化后的旧正文通过「已不在当前目录中」列表保留并可预览。只改编号不触发正文重写或规划重生成，重新合册使用当前编号。整册产物提供「预览整册」「下载标书」，版本变化后提示重新合册，预览请求带产物版本。


| 页面动作 | 原生链路 | 继续方式 |
|---|---|---|
| 开始解读 | document-parse + tender-analysis | 本阶段完成停轮 |
| 智能生成/调整目录 | 弹窗选择目标篇幅（1–1000页或不限）与编号，再执行tender-outline | 设置由程序保存到目录产物；正文保留，当前目录可编辑保存 |
| 生成写作指引 | tender-body规划 | 指引MD生成后停轮 |
| 生成承诺清单 | tender-body关键事实与承诺 | 具体值由本次操作要求或ask_user_question提供 |
| 开始/继续制作标书 | 同一dsh官方执行会话自动准备指引→承诺→补写缺失及未完成章节→检查→合册 | 具体缺值在页面回答后续接同一会话，不受当前选择章节影响 |
| 生成/更新当前章 | dsh官方循环/子Agent承接灵燕原角色与DOCX工具 | 明确册名和章节；缺失准备自动补齐，过期准备先由用户核对；更新只作用于所选章 |
| 修改当前章 | 原tender-body修订 | 明确章节范围和修改要求 |
| 开始/重新审核 | 原件解析→有效招标要点→完整逐项对照→证据校验保存→汇总报告 | 单轮审核；歧义和证据不足列为需确认，输入变化使旧报告待重新审核 |
| 合册导出 | docx_assemble_volume + tender.volume | 页面下载原生DOCX，不调用模型 |

每次生成提交携带任务、输入文件版本和request_id。重复网络提交返回同一回执；新的操作使用新编号。上游版本变化时拒绝过期提交，不自动重交。ask_user_question的具体选项在页面显示，按dsh官方callId提交结构化答案到同一执行会话。停止执行不发起新会话。具体功能页面不展示回答记录；官方会话仍存储问题与答案。三个业务列表和项目详情均无常驻「重新读取」按钮。刷新浏览器、重新进入项目详情，以及智能解读/制作/审查之间切换时，自动读取最新状态、来源选择、目录与文档；请求不使用浏览器缓存，原件和正文预览按文件或依据版本更新。业务操作后自动取数，执行中保留状态轮询。详情读取失败通过集中操作提示重试，已有数据不作为本次读取成功的结果。列表取数仍用于初次进入、上传与归档后的业务更新，后端没有独立的刷新接口。

资料库继续采用灵燕公司资料、手工章节素材块和Word版式库。素材块由用户勾选真实目录区间创建；版式库选择默认Word样式，后续新建章节与重新合册使用原DOCX业务工具。原后端的结构化身份/业绩等表单另列待讨论。

## 失败与草稿

失败集中显示在顶部短提示和「操作提示」详情，不在每个栏目下重复技术错误；同一操作去重，按当前任务显示。原始服务错误收进详情。文件预览保留重新读取入口，失败不启动生成。

保存遇到另一处修改时，保留当前草稿，提供三种具体操作：继续编辑、丢弃草稿读取最新、使用本次版本。最后一项覆盖另一处修改，原内容由灵燕保存为恢复点；不会自动覆盖。离开有草稿的栏目、导航或工作台时提供具体丢弃选择。

解读使用六栏进度取代通用“尚未发起”状态行。制作与审查有执行时显示“正在执行/有具体选项/本轮已结束/本轮未完成”。用户取消显示“已停止”；completed只表示本轮结束。没有正文时显示“尚无正文文档”，不包装成整册通过。

## 原件格式

七类格式校验在选择、拖拽和服务端一致。招标来源和资料保留100MiB限制，受审投标文件在初次上传及更新时不设固定大小上限。DOCX复用原Word工具，PDF复用灵燕组件并打包worker/CMap/字体/wasm，图片用原Blob和浏览器渲染，切换取消旧请求并释放Object URL。GIF播放原动画；文字解析只送第一帧PNG，上传原件不被替换。

参考原实现：`DocxViewer`、灵燕 `SourceView/PdfPreviewBody/DirectoryProcessor` 和原生文件API；来源见 [UPSTREAM](UPSTREAM.md)。工程范围见 [当前合入验收](MERGE-ACCEPTANCE.md)。

制作写入由官方 tools/execute 钩子在工具执行前约束，主线程与子Agent共用范围。正文写入与校验按本次章节路径串行；普通 write/edit 只用于主线程当前准备文件。已确定承诺事项不得被模型修改或删除；需要变更时提示具体差异，用户在承诺页签编辑保存。指引就绪记录绑定校验后的实际文件摘要及输入依据，文件修改后不会沿用旧就绪标记。未校验的中间文件作为未完成准备保留，可停止后继续。

承诺清单统一使用 markdown-it-py 的表格解析结果供写入保护、就绪校验、子Agent派发与正文承诺比对使用，单元格中的转义管线保留为完整值。空事项、空值或缺少必需列的行不得写入或标记就绪。已保留的重复事项中间文件允许去重，但修复必须保留每个已确定值；同事项出现冲突值时由用户在承诺页签处理，模型不能任选其一。


## Markdown 解析统一

Python 业务代码只通过 `app/markdown.py` 使用 markdown-it-py（CommonMark、表格、双波浪线删除线）。承诺清单是业务字段适配器，不再持有独立 Markdown 解析器。以下结构消费均使用同一入口：

- 分析产物的 coverage 标题、出处表格与原文行号校验。
- 写作指引的就绪校验、章节派发、图示核对与管线状态检查。
- 承诺清单的写入保护、就绪记录、章节派发与正文值比对。
- 来源登记表 MAND/TPL/REQ/SCORE、响应文件、目录列表、来源标注、目录说明与项目信息组装。
- 招标解析、公司资料及素材库共同使用的带行号标题大纲和检索分段；素材比对、知识库与素材摘要按解析后的语义文本读取。

前端展示、业务编辑及服务端模型 JSON 代码块读取共用 `shared/markdown.js` 的 unified/remark-parse/remark-gfm 配置。Python 与 JavaScript 使用 `tests/fixtures/markdown-contract.json` 的相同样本核对标题、表格文本、空格补列及原始行号；前端编辑仍按 AST 原文位置替换业务字段，保存保留出处与关联。目录章节与资料行区间在单独读取时保留整份文件的引用式链接定义，避免截取后把链接语法误当成标题或正文值。

已删除手写管线拆表、正则识别 Markdown 标题、按缩进字符数构造列表，以及正则剥代码围栏。表格缺少分隔行或表头/分隔行列数不匹配时是普通段落，不保留旧格式兼容。分析校验按各节模板核对必需表格及完整表头；无条目也保留空表，格式要求必须同时保留章节表和模板表。缺表、错误表头或代码块中的示例不能满足契约，不能作为零条引用校验通过。表格之后的散文必须用空行分段，准备校验会拒绝混入表格的无效行。

工作文件路径由 Python `app/work_paths.py` 和 Node `native/work-paths.mjs` 统一处理，使用同一跨端路径样本验证。入口接受 macOS/Windows 的相对路径分隔符与 `./`，业务键和接口返回一律使用 `/`；文件系统落点使用原生路径。绝对路径、盘符、UNC 和目录越界被拒绝，解析文件只读及准备文件校验按实际文件身份判断，链接和大小写别名不能绕过保护。工作台读取、保存、DOCX 工具、校验、执行范围及生成状态采用一致口径。

PDF/Word 转 Markdown 保留原生转换器，并对表格里的字面竖线与反斜杠转义；转换输出的行数与元素映射不因转义改变。原文按行区间读取、元信息修订头、PDF 页码锚点、Word 标题编号和领域字段（来源 ID、图示类型等）不是 Markdown 语法解析，继续遵循原业务契约。DOCX 校验中的 Markdown 残字检测也保留，用于发现交付稿中意外打印出的符号。

## 审核页面

外部文件入口使用与解读、制作相同的上传组件，分别选择招标和投标文件。审核详情头部集中运行状态、停止及重新审核，更新/预览招标与投标文件操作位于重新审核左侧。报告为概览、问题清单、招标要点与对照三个页签；摘要编号展示，问题按可能废标、评分失分风险、需确认、建议修改分类。前序要点不能限制实际回查引用范围；真实原文中的限定、例外或冲突须并列进证据卡。

只进行一轮业务审核，程序校验关联、范围、完整性与版本；没有独立模型复审。同一审核Agent可在本轮结束前修正先前批次。制作后的原DOCX检查是程序检查，报告状态不等于所有图片、平台操作或实际评分已经核验。方法来源与已知边界见[当前审核实现](REVIEW-CURRENT.md)。
