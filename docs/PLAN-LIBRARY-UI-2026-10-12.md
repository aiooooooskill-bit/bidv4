# 资料库正式接入与全项目 UI 统一实施计划

日期：2026-10-12

计划依据：用户已测试并认可资料库隔离体验；确认写作素材不区分主体；认可 UI 规范，并要求整理实施计划。本文件是实施计划，本轮不修改正式业务代码或数据。

## 一、已确认的目标

1. 公司资料和授权代表按投标主体分别管理；项目在开始制作前确认主体、签字代表和本次签署日期。
2. 全部解析信息可查看、核对、修改，能对照识别原文和原件；人工核对值供检索及制作使用。
3. 写作素材统一入库，不绑定投标主体；提供真实关键词检索、来源筛选、结果列表和分页。
4. 公司档案中的地址、电话、传真、邮箱等常用值一次维护，制作时直接读取；只询问确实缺失或本次项目需要确认的值。
5. 将已经认可的视觉应用到智能解读、标书制作、标书审查和资料库；统一控件与状态，各模块保留适合业务的布局。
6. 尽量复用现有后端机制，不更换 OCR/解析、AI 整理、FTS5/jieba/BM25、DOCX 注入、章节修订及合册链路。

固定边界：公司资料属于一个主体；授权代表属于一个主体；写作素材全库共用；每个项目当前确认一个投标主体和一个签字代表。联合体、多家共同投标、多级组织权限、素材版本平台不纳入本轮。

## 二、现状与正式接入差距

| 能力 | 已有基础 | 正式接入要补的内容 |
|---|---|---|
| 资料管理体验 | 原型已认可，左列表右详情、字段编辑、原件对照 | 正式组件拆分、真实服务接口、稳定保存与并发控制 |
| 公司档案 / 授权代表 | 原型附加表及页面已验证 | 正式存储、校验、来源记录、项目引用 |
| 图片识别 | 已上传开户许可证有真实 OCR 和 AI 整理结果 | 正式页面接入现有识别任务、处理失败 / 重试 / 核对状态 |
| 公司资料检索 | 正式使用 FTS5 + BM25 | 主体边界进入 SQL；列表及生成工具一致遵守 |
| 写作素材 | 现有 DOCX 解析、建块、检索和注入工具 | 正式列表全文检索、来源筛选、分页与预览 |
| 项目制作 | 写作指引、承诺清单、正文与合册已经能运行 | 制作前主体确认；常用信息进入当前生成依据与投标函 |
| 新 UI | 规范、CSS 变量和组件示例已交付 | 替换正式样式，覆盖真实业务状态与短屏场景 |

原型中的第二个主体、演示文件、24 个素材块，以及体验时新增的测试记录不作为正式企业事实导入。体验库只验证设计；正式使用的来源仍是用户真实上传资料及核对后的公司信息。

原型没有调用新图片的 AI 识别，也没有运行正式投标函生成或 AI 项目化修订。正式验收必须补齐这些环节，不能把「页面显示可填入信息」当作「真实投标文件已正确写入」。

## 三、实施方案与取舍

### 先检视不成立的假设

只替换 CSS 无法解决重复询问：现有制作链路并没有明确的项目主体绑定和公司常用信息来源。把每张证件的 OCR 自动合并进公司档案也不可靠；旧证件中的法人、开户信息可能已变化，一张开户许可证没有电话、邮箱或通讯地址。

直接把原型整体接入正式项目会引入临时服务、演示数据及不完整的生成衔接；将全部模块强制改为同一列宽也会降低目录和文档工作的效率。

源码还显示两处需要补齐的工程问题：`db._now()` 是秒级时间，原型仅凭 `updated_at` 不足以识别同一秒的并发修改；`ingest.finish()` 当前将 AI 结果同时写入 suggested/business，重识别可能覆盖人工确认值。它们应在公司资料正式保存切片中解决。

### 可选推进方式

| 方式 | 结果与代价 | 判断 |
|---|---|---|
| 先整项目换肤，再处理资料绑定 | 视觉改善快，但重复询问和主体混用仍在 | 不作为优先方案 |
| 直接搬入整套原型 | 展示快，但重复建设服务、存储和任务流程 | 不采用 |
| 按端到端切片接入资料、制作，再统一剩余页面 | 每阶段可运行、可验证，复用现有后端，逐步消除实际问题 | 推荐 |

推荐第三种：第一阶段让一个真实文件从上传走到核对保存和检索；之后完成写作素材管理，再完成公司信息进入真实投标函。公共 UI 随这些切片统一，最后覆盖其他页面。

最大未知风险是生成阶段仍依据旧承诺清单或旧公司信息继续写作。因此正式验收重点放在「输入依据更新、主体切换、未完成任务、真实 Word 产物」上。若端到端验证失败，优先修复这一条链路，暂停扩大页面改造范围。

## 四、阶段与交付

| 阶段 | 工作范围 | 可评审交付 | 验收后进入 |
|---|---|---|---|
| P1 | 公司档案、代表、公司资料核对；公共 UI 基础 | 正式资料库能处理一个真实图片 / 文档 | P2 |
| P2 | 全库写作素材检索、来源筛选、分页、建块与预览 | 素材从上传到可检索和注入实际 Word | P3 |
| P3 | 项目主体确认、常用信息读取、生成依据及真实投标函 | 已有公司信息进入投标文件，减少重复提问 | P4 |
| P4 | 解读、制作、审查及公共弹窗 / 提示全面统一 UI | 四模块外观一致，业务操作保留 | P5 |
| P5 | 真实文件综合验收与正式交付 | 验收记录、已知边界、可运行正式版本 | 完成 |

不先建设大而全的平台。每个阶段包含存储 / 服务 / 页面 / 验证所需的最小完整链路，不把所有后端写完后才开始前端。当前计划不承诺未经评估的工期；按各阶段验收结果安排后续工作。

### P1：正式公司资料闭环

**范围**

- 将资料库拆为主体、授权代表、公司资料、写作素材及 Word 版式页；保留现有 Word 版式上传和默认选择能力。
- 主体档案维护名称、统一社会信用代码、注册地址、通讯地址、电话、传真、邮箱、法人姓名及职务、开户行及账号、备注。
- 授权代表维护所属主体、姓名、职务、电话、邮箱和说明；左侧列表支持主体筛选和统一分页。
- 公司资料详情分为整理信息、识别全文、原件对照；展示所有 fields/extra、内容说明、检索问题、出处与状态，支持保存和取消。
- 人工核对值写入当前 business metadata，AI 提取结果保留为 suggested metadata；保存后按现有重建入口更新 FTS。
- 上传由现有服务进入现有识别任务；提供实际进度、失败原因、重试和待核对状态。
- 从已归属并核对的资料按字段读取候选值，逐项采用到公司档案并记录来源；不自动覆盖当前法人等信息。
- 公共颜色、字号、按钮、输入框、页签、提示、分页先接入本阶段；未保存保护复用现有 NavigationGuard。

**正式存储选择**

- 在当前项目 Schema 中增加主体、代表、公司资料归属、资料核对版本、项目投标上下文的必要实体；以稳定 ID 关联，不以可修改的公司名称关联。
- 公司资料归属用独立关系记录连接现有 kb item，不修改源文件路径或把主体名拼进目录。
- 新实体由当前 Schema 初始化；不写 migration，不批量重建或清空旧资料。已有正式资料没有归属记录时显式显示「待确认归属」，经用户核对后绑定；不自动猜测归属，不回退到全库使用。
- 原件始终保留；初次识别文字单独保存。更正后的识别文字、outline 和索引须一致，原件 / 原始转写 / 当前核对值能分别查看。
- 保存采用单调递增 revision 和原子 compare-and-set；不继续用秒级 updated_at 作为唯一并发判断。旧版本提交返回冲突并保留表单输入。
- 重新识别只更新新一轮 suggested 结果；已人工核对的 business 结果及公司档案保留，差异待人工采用。识别中禁止同一条资料重复启动识别，保存与任务回写使用同一套版本约束。

**验收**

1. 用现有开户许可证核对全部字段、出处和原图，确认归属后可保存和再次读取。
2. 修改一个字段后，用新值检索能命中；原始 AI 字段和原件保持可查。
3. 新上传真实图片走正式 OCR / AI 整理任务；失败可重试，模型输出不直接被标为人工已确认。
4. 两个真实或明确演示的主体分别检索，A 的公司资料不出现在 B 的项目检索中；未归属资料不进入生成。
5. 同一秒两页面保存同一资料时，旧 revision 被拒绝；重识别不覆盖人工核对值。
6. 代表列表超过一页时，筛选、分页、详情定位和未保存保护正确。

### P2：全库写作素材闭环

**范围**

- DOCX 上传 → 原有解析目录 → 勾选章节区间 → 建素材块 → 检索列表 → 查看正文 / Word 原件。
- 列表检索标题、用途与全文，不再仅在前端做标题字符串过滤。
- 来源文件筛选、总数、每页 5/10/20 条与翻页；筛选改变回到第一页，结果按稳定顺序排序。
- 名称和用途可修改，保存后重建相应素材索引；正文仍取所选源文件区间。
- 写作素材不存主体归属，不增加主体筛选，不因项目主体不同限制检索或注入。
- 继续调用真实 docx_material_inject，按整块或所需行号区间注入；图表及样式来自原 Word。

**检索实现边界**

- 页面和生成工具共用同一组检索规则，保持 jieba/FTS5/BM25。
- 先限定资料域：公司资料为 kb，公司条件也进入查询；素材为 mt，全库查询。再排序、截断和分页，避免先取全库前 N 条再过滤导致漏召回。
- 总数、来源计数和分页使用同一个关键词条件；来源计数在选择某个来源前统计，便于切换。
- 不在本阶段引入向量库、另一套 RAG 服务或搜索配置平台。

**验收**

1. 上传带标题、表格和图片的真实 Word，勾选章节建块后，能按只存在于正文中的关键词命中。
2. 来源筛选、总数、分页无丢失 / 重复，修改用途后可按新词检索。
3. 不同项目主体检索相同关键词时可获得相同全库素材范围。
4. 注入实际 Word 后检查图片、表格、编号及样式；超出素材授权区间的请求被拒绝。
5. 正式生成仍执行「检索 → 拷入 → 按项目修订 → 扫残留」，不能把注入成功当作章节完成。

### P3：公司信息进入真实标书

**范围**

- 创建项目时可暂不确定投标主体；开始写作指引、承诺清单、正文或完整制作前，必须在项目准备区确认主体。该规则后端执行，不能只禁用页面按钮。
- 选择本主体的法人或授权代表；签字代表姓名 / 职务来自所选人员，签署日期明确为本次项目值。
- 项目准备区读取已维护公司字段，展示实际取值及来源；无传真与未维护传真分别表示「无」和缺失。
- 已有地址、电话、邮箱等直接交给生成上下文；只对真正缺失、冲突或项目特定的值提问。
- 短字段用紧凑输入控件；缺失信息按主体常用信息 / 人员选择 / 项目特定信息组织，不平铺七个大文本域。
- 更新主体、代表、日期或被采用的资料后，进入现有 preparation / input version / stale 检测机制；已有文件保留，后续制作与导出在当前依据上校验。

**关键设计**

项目确认保存引用 ID，并保存本次采用值的快照、来源引用与修订号。生成阶段使用已确认的项目快照，不在长任务中不断读取正在编辑的公司档案。公司档案或已采用资料有新版本时，项目显示需要重新核对；用户重新确认后产生新的项目依据版本。未被采用的其他资料变化不使所有项目无差别过期。

项目上下文的变化加入 page_flow.input_versions、build_state.preparation_stamp 和相关正文依据，不另建一套制作状态系统。更新主体时不得沿用上一主体的已确认事实和代表；项目日期等本次值保留但需核对。已有承诺的变更通过现有人工编辑 / 校验入口明确处理。

任务运行或等待答复时不允许修改其主体上下文；要更改则先停止当前任务，再重新确认依据。这样避免同一生成任务中途切换公司。

search_company_assets 从当前 task/run context 取得主体范围，由后端限定；Agent 不自行传入任意主体。公司资料的正文、附件、原图及关联证明的项目级读取与引用均检查主体关系。库管理页可以查看全库，但项目制作不能因无命中放宽到其他公司。普通搜索过滤不被宣称为完整的文件系统权限隔离；直接文件读取和附件插入路径需要一并审查，避免绕过项目归属检查。

**验收**

1. 主体档案字段齐全时，真实生成投标函不再重复询问截图中的地址、代表、电话、传真、邮箱等已有值。
2. 缺一个电话时只出现相应补充项；签署日期仍按本次项目确认，不从历史证件推断。
3. 生成 Word 的公司名称、地址、代表姓名 / 职务、联系方式和日期与项目确认值一致，附公司材料来自本主体。
4. 换成 B 主体后，旧 A 事实和代表不被继续写入；准备及相关章节标记需核对，旧 Word 保留。
5. 修改未被该项目采用的其他资料不会无差别使其全部章节失效；修改已采用依据能被发现。
6. 已有生成、单章修订、继续任务、停止、合册和导出能正常执行；等待补充的任务不会丢失已填写内容。

### P4：剩余页面统一 UI

**范围**

- 项目列表与主导航：浅灰页面、白色卡片、统一统计、筛选、按钮、页签和状态。
- 智能解读：原件 / 结果对照、阅读层级、编辑、依据入口和解析状态统一。
- 标书制作：目录 / 正文 / 预览保持业务布局，任务进度、当前章操作、缺失项、保存与合册操作采用同一规范。
- 标书审查：问题列表、风险标签、证据、章节跳转及复核反馈统一。
- 上传、设置、Word 版式、证据抽屉、错误反馈、未保存对话框统一。
- 将设计变量接入 src/plugin.tsx 的样式入口，按模块删除被替换的旧 CSS，不以不断追加覆盖层实现换肤，不保留双套主题或 fallback。
- 使用现有 Modal、NoticeCenter、NavigationGuard、DocxViewer、SourcePreview，不新增 UI 框架依赖。

**验收**

1. 四模块主按钮、字号、圆角、表单、状态、分页一致，宿主 dsh 界面不受污染。
2. 1366×768、1440×900 及窄屏布局中，保存、分页、停止、合册等主要操作可达。
3. 检查真实空、加载、失败、运行、等待输入、成功和未保存状态，支持键盘及焦点恢复。
4. Word/PDF 原件及导出文件内容样式不因应用 CSS 改变。

### P5：综合验收和正式交付

使用用户真实招标项目、真实公司证件和真实写作素材完成一轮：维护主体 → 上传 / 核对 → 代表选择 → 制作准备 → 素材检索 → 正文生成 → 修订 → 审查 → 合册下载。

验收检查现有指引 / 承诺文件、实际 DOCX 内的值、图表、来源和旧名称残留。不能只看浏览器截图或接口 200。

工程验证按改动范围运行现有 TypeScript 检查、构建、前端及业务测试，增加必要的主体隔离、人工核对保护、并发冲突、依据过期和真实 DOCX 检查。整体交付前运行现有 npm run verify，并完成浏览器人工验收。

交付当前正式版本、变更文件清单、验证证据和明确的剩余边界。生产资料不清空，测试数据不进入正式库。改动前保留可恢复的工程与业务数据快照；该快照用于恢复，不在代码中保留旧功能、兼容分支或数据库 migration。现有目录不属于 Git 仓库时不凭空声称已创建分支或已提交；先保证恢复点可查，再修改正式代码。

## 五、代码落点

以下为职责分配；新增文件名按实现时的最小模块边界确定。

| 区域 | 主要落点 | 处理 |

| 资料与素材 API | business/python/app/services/knowledge.py、materials.py、routes.json | 明确请求结构，增加核对保存、列表检索和分页；复用现有上传 |
