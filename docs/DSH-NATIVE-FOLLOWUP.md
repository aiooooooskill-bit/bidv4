## dsh官方图片说明与实测

[官方模型配置说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/guide/providers.md#image-input)明确：自定义pi-ai模型未声明图片且没有目录继承时，默认按text处理；可在现有模型条目设置`input: [text, image]`。设置页面路径为“模型 → 编辑提供方 → 自定义设置 → 模型选项 → 输入类型 → 图片”。本机0.2.0-rc.2的`dsh-client-ui-settings-models/lib/client.js`确有该控件，pi-ai配置类型也接受`input`。

该字段是能力声明，不是端点探测。`dsh-tool-fs`的`assertImageCapableRoute`在模型请求前检查声明；因此首轮read_image被拒绝不能证明本地模型没有视觉能力。官方文档同时说明，声明错误的模型会由提供方拒绝请求。

实际诊断仅在独立Cordis宿主内补充图片声明，不修改正式profile、地址、模型选择或凭证。使用同一`lmstudio / mlx-community/Qwen3.8-27B-4bit`：真实Agent调用官方read_image → 工具保存图片附件并返回ImageBlock → pi-ai发出含图片的请求 → 本机8000模型正常返回，turn/end为completed。正式配置及凭证文件摘要前后一致，未连接3188。

验收只断言真实图片工具结果、模型请求中的ImageBlock、正常结束及正式配置不变，不判断模型转写内容。初次诊断脚本曾加入不属于本轮范围的合成数字一致性断言，并错从结果消息读取工具名称；已按工具callId关联修正，仅采用传输验收。保留初次诊断记录，不将其混作OCR内容质量结论。

结论：**同模型图片通路隔离通过，完整OCR尚未接入。** 正式宿主仍缺该模型的图片声明；后续在dsh现有模型配置中启用，不增加招投标插件模型/OCR表单。

OCR接入继续复用灵燕的PDFium分页、转写规则、页序与MD/大纲/元信息契约。`app/parse/image.py`已有转写提示词，但直接导入会拉入旧`vlm.py`模型客户端；需要提取规则并通过dsh模型服务调用，删除旧模型选择与客户端。扫描/混合PDF、GIF首帧、分页聚合、取消及原页面展示仍需工程测试。

本机pi-ai默认请求图片预算为单图4,194,304像素/1MiB、请求图片合计20MiB；来源文件100MiB上传限制不等于视觉请求预算。采用宿主图片处理并分批，不静默丢页。
