# 大文件审核链路排查与容量验收（2026-10-14）

本轮在隔离工作树完成，未上线。取消的是受审投标文件固定字节上限；招标来源、素材及其他上传仍按原有范围限制。未改变审核业务分类、评分后果或增加独立复审阶段。

## 解析与内存的区别

实际链路：原件流式上传到磁盘 → 确定性解析为 Markdown / 大纲 / 元信息 → 审核 Agent 读大纲、分段精读并回查后文 → 分批保存原文证据 → 全部要求齐备后发布报告。

原件未整份送进模型。原灵燕固定源码 de909f12572b4c469864b12255e26cc185ada7ec 的 sidecar/app/parse/docx.py 第76行调用 python-docx Document，第125行统计 package.image_parts。这个通用库加载关联图片，使“先转MD”过程本身仍可能大量占用内存。当前原件只读，正文/样式/批注由同一库解释，图片与内嵌附件不再解压到文字解析器内；表格、标题、图片占位和计数保留。报告末尾原DOCX检查也采用同一文字加载方式。杭州真实投标的转换结果逐字一致。

这段解析→MD→分段审核与灵燕流程一致；此前查出的强制七类前置分析等平台新增流程仍客观存在，本次容量修复不代表已完全复现原灵燕整套业务流程。

## 已发现与已修复

| 环节 | 原问题 | 处理 |
|---|---|---|
| 选择、更新投标文件 | 前端100MB限制 | 按文件用途取消投标限制，保留格式校验 |
| HTTP上传 | Busboy100MB限制 | 仅投标上传不设fileSize，流式落临时文件 |
| 任务来源落盘 | Python100MB限制 | 投标按1MB块写入并原子替换，不设固定字节上限 |
| Word转MD及收尾检查 | 图片二进制被整包加载 | 只载所需XML文本，原件和图片保持原样 |
| 引用及行数 | 每个证据重复整份读Markdown | 流式计行和读取所需区段，原引用合同不变 |
| 扫描PDF | 超过128页直接失败、提前渲染全部页面 | 移除页数硬上限，识别当前页前才渲染，全部输出齐备后才发布 |

## 实测结果

材料是合成工程压测文件，不是实际投标书。正文含12000条索引、文末培训/交付承诺和64/128张实际引用的有效PNG，ZIP采用存储模式。四条招标事实及八份结构化要点预先建立并通过校验；真实模型独立定位投标证据并作出对照结论。

| 文件 | 实际上传 | 首次转MD | 文字解析进程峰值RSS |
|---|---:|---:|---:|
| 539,969,255 字节 | 1.01 秒 | 3.99 秒 | 88.4 MiB |
| 1,077,429,619 字节 | 1.92 秒 | 4.32 秒 | 106.2 MiB |

1.08GB样本经当前配置的本地 Qwen3.8-27B-4bit 模型完成约176.9秒审核；4条要求全部保存为已响应，报告状态已审核。模型实际读取了Markdown大纲、开头短段和12004行之后的后文章节，并用实际原文引用培训与文档承诺，没有把1.08GB原始文件送进上下文。一个不合格的批次引用被程序拒绝后，由同一个审核Agent修正保存，不是第二轮业务复审。

原python-docx全包加载同一1.08GB文件，峰值RSS约636.4MiB；当前独立测量约106.25MiB。上传程序、宿主和浏览器的总内存未包含在这项解析进程指标中。

129页扫描PDF通过完整性契约测试：按需渲染、少一页拒绝发布、129页输出齐全才能发布。该项使用工程转写文本验证程序，没有实跑129页真实模型OCR。

Python493项、界面21项及原生链路1项通过；类型检查和构建通过。招标来源540MB实际HTTP上传仍返回413，且不留下来源残文件。原杭州真实报告文件哈希不变。

## 尚未证明或仍有限制

- DOCX内嵌图片仍为图片占位，证照/合同图片内容不等于已识别和核验；其业务影响应列为需确认。
- 浏览器原件预览仍会获取整份DOCX/PDF并渲染，和服务端审核互相独立。本轮没有证明GB级原件预览稳定。
- 文件字节大不必然导致模型上下文大；正文XML极大或要求极多时，文字解析内存、工具返回大小、取证完整性及模型上下文仍须另测。四条义务合成验收不能推广为任意几千页实际招标全部语义覆盖。
- 扫描页识别耗时随页数增长，仍依赖模型图片能力；当前图片2000万像素预算未改变。长OCR中断后没有逐页结果恢复机制，不能把部分识别当完成。
- 固定投标字节上限已取消，实际可用磁盘和宿主慢上传超时仍存在；不是无限资源承诺。
