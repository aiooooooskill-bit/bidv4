### 1. 正文派发的并发没有真正生效：已确认，最高优先级

当前[task工具注册](/Users/ooo/Documents/AIwork/bidv4/server/native/tools.mjs:55)未声明 `isConcurrencySafe`。DSH 的 `executionMode()` 对未声明的工具返回 `exclusive`，执行循环每次只取该单个调用并等待结束。默认并发上限再高，也不会越过这个独占屏障。[官方分类器源码](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/core/tools/src/index.ts#L1311)、[调用调度源码](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/core/agent-loop/src/tool-calls.ts#L84)。

时间线与代码吻合：当前制作阶段10个子任务，5轮都在同一个模型步骤里发出2个 task，但每轮实际最大重叠数都是1；整个制作阶段模型请求最大重叠数也为1。不是模型没有提出并行任务，而是接入层按独占执行了它们。task 等待约19分55秒，包含子任务内部模型与工具时间，不能再与模型耗时相加。

按每对任务保持原耗时且互不干扰作离线计算，允许两者重叠的理想可重叠部分约7分09秒。这只是排程上界：并发会改变服务负载、文件竞争和模型耗时，不是承诺可节省7分钟，也不是实测优化结果。

### 2. 审核阶段内部仍在累积历史：已确认

当前审核的单次输入由16,811增长到386,237 token，累计8,523,957。跨阶段归档已经发生，但审核自己的原文、提交参数、错误回执和共享证据仍持续留在当前会话中。

`save_review_batch` 的工具返回累计277,364字符；其中已保存批次回执中的 `shared_evidence` 累计约190,534字符，下一批完整内容约94,603字符。这些分别统计自解析后的字段，因序列化空白等差异不能直接相加等于原始返回长度。共享证据中有309次原文出现，只有190种不同文本。共享本身有助于核对，问题在于同一已存证原文又被带回，随后继续随历史发送。

DSH 默认压缩主要用于接近容量上限时防溢出，默认阈值比例为0.8；通用工具结果剪枝也在压力触发后运行。隔离测试声明1,000,000的窗口，没有在审核中触发额外摘要。大窗口因此不等于低输入成本。盲目降低阈值、截掉原文中间部分，会损害证据完整性；应在已接受批次的业务边界处理历史。[官方压缩说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/compaction/compaction-basic/README.zh.md)。

### 3. 审核读取上下文会反复展开整套制作状态：已确认

调用链为 `review_batches.read → context → review_basis → analysis_catalog → previous_flow → build_state.snapshot → input_versions / section_basis / asset_usage`。在已完成的隔离当前组上做3次只读分析，累计约3.31秒，出现4,385次数据库连接、13,155次数据库执行、3,327次资料状态检查。该耗时带分析器开销，不能直接外推为每次生产耗时；高重复调用数量及展开路径是确定事实。

本次审核保存回执30次，中位约3.8秒；其工具跨度累计约80秒。保存还会在候选校验与最终接收时重复核验，这是有价值的安全边界，但同一不变输入的中间派生结果没必要反复递归计算。见只读分析记录（已清理）。

### 4. 正文的模型轮次仍然很多，推理预算并非本次主因

两组制作阶段都是242次模型请求。当前组正文输出234,487 token，其中159,725为提供方记录的推理 token；对照分别为161,545与99,801。当前组该阶段模型请求时间并集比对照多约320秒，工具时间反而减少约53秒，最终制作变慢约268秒。独立生成的内容、图表和推理长度不同，不能只凭此认定增大输出上限导致了变慢。

两组本次均为0次输出预算耗尽、0次HTTP错误。提高预算和补充耗尽诊断没有在这次完整运行中体现“减少耗尽次数”的可测收益。灵燕代码的 run 默认思考档为low并明确注入；我们随宿主/适配器选择，本次隔离请求记录未显式指定推理强度。这是需要同条件验证的差异，不能据此声称正式环境设置错了。

### 5. 参数、路径、引用错误还会触发修复往返

对照工具错误27次，当前34次。当前分布：解读2、目录7、制作10、审核15。错误包括标题未先建立就绑定、产物契约名不完整、资料路径域混用、修订坐标/期望原文不匹配、审核准备尚未结束就取依据、把背景和响应义务混判，以及没有保留完整出处。严格参数检查和证据卡切段修复解决了部分失败方式，未解决整个链路的调用纪律。

只调整模型请求重试次数无助于这些错误：它们是模型得到业务错误回执后的新一轮调用，通常不是HTTP请求失败。不能放宽引用、适用性或质量校验来掩盖重试。

## DeepSeek框架中可以自定义控制什么

| 可控位置 | 官方机制 | 本项目建议 |
|---|---|---|
| 自有工具是否并行 | `ToolDefinition.isConcurrencySafe(args)` | 仅为有明确资源边界的正文派发及只读工具声明安全；不改DSH内核 |
| 同一步工具并发量 | `agentLoop.config.maxParallelToolCalls`，默认10 | 首轮以2路验证。只增上限不会改变独占工具 |
| 子代理容量和深度 | `maxActiveSubagents`默认8、`maxDepth`默认1 | 保留有限深度；容量满会拒绝准入，不是自动排队，不能拿它直接当排队器 |
| 子代理模型/工具/角色 | `startActivation`、`agentPreset`、`agentOptions`、`tools.restrict` | 继续使用官方进程内spawn和现有角色；按阶段缩小可见工具。解读当前携带48个schema，有进一步收敛空间 |
| 请求配置 | `agent/request`、模型能力解析 | 记录实际生效的模型、推理强度和输出上限；确认适配器支持后才试不同预算，保留同模型基线 |
| 业务边界上下文 | `agent/pre-step`、持久会话与compaction区域事务 | 复用已有阶段归档机制，新增审核已接受批次的确定性归档；保留用户消息、当前证据和完整原始记录 |
| 工具回执与观测 | `tools/execute`、`tools/post-execute`、`tools/result` | 用执行层测真实工具耗时；自有工具回执改为当前必要内容与完整证据索引，避免重复整段回传 |
| 网络失败重试 | provider的 `retryPolicy` 与 `agent/request-error` | 只对瞬时模型请求错误有界重试；业务错误定点修正，不重做整本 |
| 业务工具进程 | 我们自己的 `business()`/runner | 可以自行优化请求内缓存或常驻执行；这是业务接入选择，DSH没有要求一工具一进程 |

框架现有扩展点足以完成以上优化，无需先重写Agent loop或另造工作流框架。官方入口依据：[工具扩展](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/core/tools/README.zh.md)、[子代理API](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/docs/subsystems/subagent.zh.md)、[请求扩展点](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/docs/subsystems/core.zh.md#agentrequest--waterfall)、[网络重试](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/llm/llm-retry/README.zh.md)。确切源码URL及摘要见来源索引（已清理）。

## 建议实施顺序

### 第一轮：先打通真实的两路正文并行

在现有task接入上声明受控并行，用已有章节解析结果分配输出路径；启动前确认写作指引和承诺版本已冻结、各任务章节路径互不重叠。共享规划只读，素材区间占用按现有校验原子登记；同一文档仍按路径锁串行，全部章节完成和自检后才合册。只读工具逐类审定，准备解析与读取依据等有依赖的操作仍顺序执行。

先验证两路，记录在飞请求、排队时间及取消释放，再决定是否增加并发。避免给所有业务工具统一标记并发安全，也不把审核或合册直接并行化。保留原生子任务、现有提示词与质量校验。

### 第二轮：审核完整证据落盘，当前上下文保持有界

保存成功且校验通过后，将该批完整原文、提交值、断言核查和错误修复记录保存在可回查的持久文件中。当前上下文保留用户确认、正在审核的完整批次、已完成状态及需要联动的证据索引。共享证据首次出现保留全文，已取证内容按稳定标识回查；需要作新判断时仍能取回完整原文。对完成的平衡工具单元做确定性归档，不通过模型摘要改写原始证据，不清除未完成工具或问答。

完整目录覆盖、逐字引用、适用性、风险类型、成本推导和最后的跨项一致性检查继续执行；不能以压缩为由只审局部、跳过旧批次影响，或把“引用存在”当成语义正确。

### 第三轮：消除重复状态计算及机械纠错

先在一次业务请求内复用相同版本的目录、章节basis、主体资料状态和解析文档索引，读入一次后供该次全部校验使用；写入和接收边界重新验证必要版本。不能只按文件路径缓存而忽略内容变更。候选检查与最终接收仍保留，但共用经过版本核验的纯派生结果。

目录决策保持逐项验证，可将同轮独立决策合为一次事务；先建立合法标题再绑定来源。统一schema、产物契约名、路径域和修订坐标回执，确保程序返还当前合法定位。错误只修正受影响条目，不重复整份制作。

### 后续：根据数据再决定常驻worker和模型预算

先测Python启动、导入、数据库与实际文档操作各自占比；请求内去重仍不足时，再评估一个清晰受控的常驻业务执行端，避免同时保留两套执行架构。并发恢复后，若出现服务背压，再按共享路由增加有界配速。

模型思考强度与输出上限作为单独实验，先保持写作及审核的既有质量基线；不同时改变提示词、并发、摘要和思考强度后再笼统宣称提升。
