# 标书审查：灵燕能力整合

这是本平台的流程编排技能。灵燕上游 `de909f12572b4c469864b12255e26cc185ada7ec` 没有独立的整标审核技能。本技能复用其解析技能、大纲、分段精读及证据纪律，再增加页面报告契约，不能宣称新增编排是灵燕原生审核技能。

先读 `skills/_shared/response-guidelines.md`、`skills/_shared/evidence-rules.md`、`skills/document-parse/SKILL.md`、`skills/tender-analysis/SKILL.md`。

## 1. 解析与角色

页面已选定文件并授权本轮审核，不再设置通用确认或要求聊天回复继续。调用 `prepare_review_documents`：现有灵燕解析方法生成双方Markdown、大纲和元信息，扫描页由宿主当前模型识别。沿用返回路径和document_id。

招标文件及补遗是要求依据；投标文件仅是受审对象。不得把投标文件加入招标补充来源。主文件、补遗冲突保留两条证据，列为待澄清，不自行决定优先级。

读双方大纲，用标题区间或逐词grep定位，再用带offset/limit的read精读。禁止整读全文，也不要求把全部原文塞进上下文。共享证据规则中的grep预算、批内并行和停止规则照常使用；本宿主grep的语法以工具schema为准。

## 2. 完整招标要点

调用 `review_basis(stage="read")` 获取八份要点的实际目录。

- 平台已有八份要点通过原校验时直接复用；回查本轮原件，不覆盖人工解读或制作成果。
- 需要提取时，只写返回的 `review/analysis` 路径。逐一阅读返回的八个原reference，按照原表头、证据键、coverage、废标反查词表提取结构事实、资格要求、递交要求、商务技术要求、格式要求、废标条款、评分标准，并汇总待澄清清单。各项写完可调用validate阶段校验；八份齐备且全部通过才能对照。
- 调用 `review_basis(stage="validate")` 运行原 `validate_analysis` 的表格、coverage、来源及行号校验。按错误修复本轮要点，返回catalog是本次完整核查范围。

技能中 `work/analysis` 在本次审查替换为工具返回目录；来源就绪事实以prepare结果为准，不使用制作流水线状态误判外部投标文件。用户已授权本轮连续审查，要点完成后直接进入对照，不自动生成目录或正文。

## 3. 本轮逐项对照

审查方法沿用灵燕 `_shared/evidence-rules.md` 和 `tender-qa` 的导航方式：已有有效要点优先；读取双方大纲定位区段，`read(offset/limit)` 精读，必要时按原检索纪律逐词 `grep`。不整读全文，不增加独立复审或自定义检索排序。

调用 `review_batch()` 获取当前需核查的要求和真实招标引用。按当前条款逐项回查投标正文；相同事项分散在正文和附件时一并取证。不得把早期清单未列某项改写成整份文件缺失，不改写原文阈值或条款含义。条款歧义、来源冲突或证明不足直接在报告“需确认”中列出证据、影响和待确认范围，继续审核，不让用户逐项裁决；缺少开始审核必需的来源文件或要修改业务规则、替用户新增承诺才提问。

页面保存所需的接口适配：每项以slot定位，提交status、assessment、tender、bid和problems；程序生成问题编号及关联要求。status采用 responded（要求的各部分均有证据支持文字响应，不代表外部事实真实性已确认）、conflict（双方明确冲突）、missing（已查范围未定位）、uncertain（全部或部分证据不足，说明已经支持和尚未确认的范围）、informational（招标背景信息，无投标响应义务）。保持原证据纪律的“原文事实、模型归纳、未发现、未检查、用户补充”边界，不以行业常识补全，不从图片占位推定材料缺失或真实性。

问题的risk_type按用户确认的灵燕业务口径填写：disqualification（可能废标）、scoring（评分失分风险）、confirmation（需确认）、suggestion（建议修改）。分类依据本份招标文件的后果条款与证据；不能由高、中、低风险自动映射，不能将一般差异直接推成废标或评分失分。

调用 `save_review_batch` 保存本轮结果。tender保留原要点全部出处；回查到相关条款、例外、限定或冲突原文时，提交实际读到的完整区段或增加独立区段，让全部判断依据进入招标证据卡。原要点是定位入口，不能限制本轮回查的引用范围；不自动扩展邻行，不借补充引用改写原要点或决定冲突优先级。

程序只校验当前slot完整、引用角色与范围、原要点出处保留、问题关联、原件版本；不调用模型二次判断。说明中的物理行号由证据卡生成，模型只填写证据的document_id/start/end，不手写行号或页号。

原文件、已有招标解读和投标正文不修改。后文发现更完整或相反的证据时，在本轮结束前由同一个Agent用原batch_id调用save_review_batch更正先前条目，仍完整提交该批所有slot。已保存不代表提前固化结论；没有独立复审阶段。继续当前审查清单至complete，实际未检查及待澄清事项如实保留。

## 4. 保存与页面

全部批次接受后调用 `finish_review_report(summary, limitations)`。只提交总结与实际限制，逐项结果及问题从本轮已保存批次合成；不重新传整份清单。失败报告不得计入已审核。

报告limitations明确实际未覆盖和需人工核验事项。宿主在本轮结束后程序校验全部条目、原文、关联关系和输入版本，程序校验全部有效才计入已审核。已审核表示报告完成，不能当作投标合规或人工验收通过。
