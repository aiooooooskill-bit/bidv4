# R2：目录初稿生成

对 `tender-response-docs.md` 中**每个**响应文件，就地在其 `# 响应文件：XXX` 段内补全
`## 目录` / `## 来源标注` / `## 目录说明` 三段（标注格式见 annotation.md）。

## 目录规划逻辑（对每个响应文件应用）

1. **以本次提交义务和该响应文件 scope 为边界**：先回查原文当前阶段要交的材料，再确定scope；项目概况、采购对象及未来服务范围不自动成为本次应交的方案。scope不能只概括项目主题，须说明当前交付范围；仅在该范围内规划。
2. **骨架来源**：以 format 节「结构大纲」为主线，用同 bidPart 的「必须章节」与「模板」
   对结构大纲**去重、对齐顺序、补全缺失章节**。
3. **层级规则**：每个有独立附件号/表号的条目（「XX 配置表（附件N）」「XX 偏离表（附件M）」）
   彼此平级、同一缩进层级，**严禁互相嵌套**；只有大纲本身已展开的子章节才向右缩进。
4. **无编号真实缩进**：无序列表真实缩进表达层级（每级 2 空格），不要任何编号前缀；
   可保留「附件X/表X」标注。
5. **当前适用REQ覆盖式满足**（初稿意识，专项复核交给清理①②）：本次响应需要落实的需求由相应材料承载，不为每条需求单开章，也不为覆盖背景介绍新增实质章节。范围外来源用现有exclude说明原文依据。正式投标需要方案且有真实技术要求或适用评分时，即使未指定固定目录，也应合理规划并完整覆盖，不能借范围收紧遗漏背景中的硬约束。
6. **排除程序性条款**：封装/递交/截止时间/废标/格式装订签章/合同转让/联合体/保证金/
   准入办理等不进目录。
7. **只补缺、不瞎加**：只做「补」与「升级/改名」，不删、不改名、不重排已有合理章节
   （清理留给三道修订）。
8. **跨目录去重互查**：同一实质内容（如「授权委托书」与资格审查子项「法定代表人
   授权委托书及身份证」）只保留一个目录节点；若分属不同响应文件必须同时出现，
   在各自 scope 注明边界。
9. 结构过渡节点只能组织已有提交内容，不能仅为“结构完整”新增实质性方案、证明或承诺；原文没有要求的额外响应内容，不因惯例或项目主题自动成为章节。
10. **封面节点**：每个响应文件的目录树**首节点**固定为 `- 封面`（投标文件惯例，
   分析产物明确说本次递交不要求封面时才跳过；节点名必须逐字是「封面」——
   合册程序按名识别它做封面页处理）。交付形态：招标文件给了封面格式样例且
   样例原件是 docx → `模板或附件填充`（下游拷原件+填空）；无样例或样例是
   pdf → `正文编写`（下游照样例/惯例排版成形）。
11. **目录页节点**：封面之后必须有 `- 目录`（分析产物明确说本次递交不要求
   编制目录时才跳过；节点名必须逐字是「目录」——合册程序按名识别，**机械
   生成目录页**：Word 目录域+缓存章节清单，**不写节文件**、交付形态固定
   `模板或附件填充`）。位置=前置区末尾，缺省紧随封面；招标文件有「XX 装订/
   编排于目录前」类要求时（如评审索引页须装订于目录前），把该前置页节点排
   在目录之前。**目录之前的非封面节点=前置页，合册不占章号**——正文各章从
   目录之后起编第一章，排前置页时按此语义放置，不要把正文性章节排到目录前。

## 树格式红线

每行 `- ` 开头、无编号、每级缩进 2 空格、独立附件号条目平级、不裹代码块
（详见 SKILL.md，assemble 按此解析，违反即解析失败）。
