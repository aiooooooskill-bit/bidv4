# 清理②：评分对齐（修订②，原则从老流水线逐字保留）

基于 `work/analysis/evaluation.md` 的 **SCORE 评分标准清单**，对当前目录做修订，
使目录与评分体系对齐——评分项是评委打分的直接依据，目录必须让每个评分维度
有语义贴切的落点。

**跳过条件**：evaluation.md 无 SCORE 条目（向用户声明后跳过）。

## 可以做的修订

1. **查漏补缺**：评分标准中的每一项评分维度，目录里都应有语义贴切的对应章节；
   缺失的补上相应 L2/L3。
2. **覆盖要点**：若某评分要点提示了具体子内容（如「运维流程」「实施计划」
   「业务人员指导」），确保对应章节覆盖它。
3. **核心项置顶**：分值高的核心评分维度对应的章节，在不破坏逻辑流的前提下
   尽量前置（评委阅读疲劳是真实的）。

**上述第 1、2 条的适用补充：**
- 评分项内原文明确并列、需要分别说明的独立实质子维度，须在所属章节下有语义贴切的
  L2/L3 标题；已有同义标题直接复用，不新增重复节点。仅在大章概述提及、挂接来源 ID
  或笼统放入偏离表，不视为该子维度已有明确标题落点。
- 方案、能力、服务的独立评分类别与数值参数不同；即使类别内列有字段、参数或举例，仍须
  独立标题。具体参数应指原文明确的取值、阈值、时长、频率或字段属性，不能将整项评分
  类别笼统称为“评分参数”而仅放在概述。
- 即使初稿结构大纲未展开这些子维度，评分对齐阶段仍应补足上述标题；不因初稿层级
  规则或父章范围已经覆盖，就将明确评分分类全部推迟到正文阶段。
- 标题须保留原文区分并列类别的限定词与对象；不能将某个子类别缩写成覆盖父章的泛称，
  仅在概述中说明区别不够。同义改名也须让评委从标题直接分辨各独立评分子维度。
- 该补充只针对明确的独立实质评分子维度；参数、数据字段、举例及证明材料不机械
  逐项拆成标题，一般 REQ 仍可由合理章节范围覆盖。
- 分类细化须遵循本项目明确的格式骨架及已有目录（如有），保留原一级章、独立附件层级、
  原有有效内容及来源标注，错标须回读本项目依据核实后更正；未规定的按本项目语义组织，
  不套固定章名，也不为凑层级拆标题。
- 原一级综合章明确列出多个方案类别时，按本项目适用类别设L2，相应独立评分子维度设L3；
  已有同义方案标题直接复用，不跳过所属方案类别把子维度直接列为L2。
- 按本轮冻结 `headings` 逐个落实真实路径；不同独立子维度不能用“与/及/、”合成一个
  标题抵消缺项，也不能与所属方案类别并列而错挂。既有附件节点不改为新主题容器的子节点。
  原节点、scope、交付形态、归位理由和概述逐字保留，新增细节追加；来源按本轮registry
  与bindings核定，旧错标纠正但不丢有效来源。原文引用中未被摘要列出的实质细点仍须纳入
  对应节点概述或已有材料范围，不因已有大类标题而丢失。参数与得分档次不强制逐项成标题。

## 禁止与边界

4. **排除程序性条款**：封装、递交、截止时间、废标项、格式/装订/签章、合同签订及转让、
   联合体、保证金等属于招标流程/程序性条款，不进目录。
5. **只补缺/升级/改名，不瞎加**无依据章节；**已存在的合理章节不要删**。
6. **保持格式**：每行 `- ` 开头 + 无编号 + 真实缩进。

## 操作方式

读当前 `## 目录` 与 SCORE 清单 → 逐项核对评分维度的落点 → 新增/升级节点补
`来源标注 :: SCORE-xx`（可与已有 REQ/MAND 并挂）与 `## 目录说明` 行（概述里写清
该章如何回扣评分要点）→ 保持其余内容原样。

评分对齐不能替代完整性核对：格式条款及响应文件组成明确命名的方案类别，仍须结合
本项目需求、用户要求和context.body_inventory逐类判断适用性并归集内容。独立类别
即使无单独分值也不能因此漏掉；不能只补有评分的一类，把其余适用类别整体略过。
本册原一级、独立附件层级、原概述与归位理由继续完整保留。主线程将读取实际标题
核对分类与原内容，不以子代理返回摘要中的“全部覆盖”为验收依据。
复用原节点时，同时核对该节点全部REQ/MAND/TPL/SCORE标注与当前registry真实条文是否相符。
仅重跑评分对齐也不能保留已发现的需求错标；不能把“编号存在”当成有效来源，或只改SCORE而留下错REQ。
错标仅纠正来源挂接，原章节、归位理由及概述继续保留；有效来源完整保留。
