# 投标目录生成（tender-outline）


Markdown 产物使用标准标题、列表和表格：表头与分隔行列数必须相等；单元格中的字面竖线写为 `\|`；表格前后留空行，备注另起段落。代码块只是示例，不作为实际章节、表格或来源登记。

## 概述

先读 `skills/_shared/response-guidelines.md`（用户回复规范）。缺节/新文件的降级影响、
三道清理的跳过原因必须向用户声明。向用户转述流程时用实际名称与
顺序（响应文件分解、目录初稿、查漏补缺、评分对齐、走查定稿、组装发布），
不说 R1/R2 等内部代号，不把三道清理改名或新造说法（如「查冗」）。

一进一出：输入 `work/analysis/` 要点产物，输出 `work/outline/tender-response-docs.md`
（目录中间态；多册并发时各册先落 `work/outline/fragments/<册名>.md` 再合并），经
`assemble_tender` 组装发布为 `tender.directory` 成果（任务内唯一当前版本）。

**路径约定（任务分组目录）**：本技能所有 `work/…` 路径都在**当前任务目录**下——任务目录
前缀（形如 `t_ab12…/`）见任务上下文的「任务工作目录」行，读写文件的路径必须带该前缀
（如 `<任务目录>/work/analysis/structure.md`）。

流程：R1 响应文件分解（有确认点）→ R2 目录初稿 + 三道清理（查漏→评分对齐→走查；
单册由主线程就地做，多册并发派发 `tender-outline-writer` 子代理每册一个）→
合并 fragments（多册）→ 组装发布。

页面输入的 page_target 与 numbering 是本轮目录设置，组装发布时由程序保存到目录成果。page_target=null 表示不限篇幅，否则按整册目标规模规划章节和重点，禁止将目标页数当作必须添加无依据章节的理由。numbering 只用于显示与合册，不写到目录名称中。已有正文在目录调整后保留，不删除、不改写。

## 执行流程

### 第 0 步：前置检查

调用 **`check_pipeline_state`**（无参数）拿事实状态，按返回裁决：

- `[analysis]` 无产物 → 引导先跑 tender-analysis。
- **缺节允许跑，但必须声明影响**（写进产物 `## 项目信息` 段，并向用户说明；缺哪些节
  读 `[analysis] 缺：…` 清单）：缺 requirements-format → 无骨架输入，目录质量明显下降，
  建议先补该节；缺 requirements-business → 跳过查漏补缺；缺 evaluation → 跳过评分对齐。
- `[freshness]` 有「解析生成=… 晚于 …」条目 → 招标文件在分析后被更新过，提示用户
  「建议先重跑分析」，由用户裁决，不自行混跑。
- `[untracked]` 有未纳入来源集合的新文件 → 提示用户「有未分析的新文件，建议先补跑
  document-parse 与 tender-analysis 再生成目录」，由用户裁决，不自行混入。

### 第 1 步：R1 响应文件分解（references/response-files.md）

读 `work/analysis/structure.md`（标段/文件关系）与 `work/analysis/requirements-format.md`
（结构大纲/封装分册要求），识别本次投标要交的**逻辑响应文件集合**，写出
`work/outline/tender-response-docs.md` 骨架：顶部可选 `## 项目信息`（从 structure.md 取
项目名称/编号等）+ 每个响应文件一个 `# 响应文件：X` 标题 + scope 段落。

**确认点（本技能最重要的一次裁量）**：响应文件划分影响下游全部工作。两问测试：
① 拆分存在多种合理方案或证据不明吗？② 划分错了下游要大面积重做吗？
②恒为「是」，所以只看①——多方案或证据不明时，用 `ask_user_question`：question 第一行
问选哪种拆分方案，换行后说明「拆分决定下游目录结构与各册分工，选错会大面积重做」；
候选拆分方案列成 questions[].options 的 label/description 对象数组，让用户在页面选，
用户可在补充里直接给改法；方案唯一且证据充分时
径直继续。

### 第 2 步：R2 目录初稿（references/generate.md + references/annotation.md）

**派发依据与原结构约束**：先 read 页面指令给出的 `context_path` 和 `facts_path`，
实际回读本项目registry、评分原文和baseline，不能只依据格式大纲或待澄清项派发。
先用 `outline_plan(operation="begin")` 承接分册骨架：已有目录不传参数 即自动保留原一级、
顺序与来源；新目录逐册填volume及root_titles（一级标题换行分隔）。此时暂不complete，不预先根据旧综合章
概述把独立评分子维度判成参数。多册随即按下文派发，task填写response_file为本项目完整册名；
单册先按原文写实际目录并完成三道清理。有SCORE评分时，单册也追加task派发同一个
tender-outline-writer对该册独立评分对齐，写指定fragment，再由主线程原样回收；有评分的
目录在真实子代理完成前，程序拒绝decisions和complete，不能用主代理预判跳过。无SCORE
单册沿原流程就地执行。已有多册从汇总恢复时，方案/能力/服务类评分仍仅有
综合章的册，先重派该册做评分对齐，其余册不动。
原一级综合章若明确列出多个方案类别，先按本项目适用类别设二级，再把相应独立评分
子维度归为三级，已有类别标题直接复用；不得把子维度直接列为二级而跳过所属方案类别。
不能只对齐评分：格式条款、响应文件组成及已有正文明确列出的方案类别也须逐类核对。
依据context.units中的方案类别，综合本项目要求、用户明确要求和已有正文判断适用性；
适用类别分别补实际二级标题，再按其内容补三级。无评分、正文尚缺或其他章节未读到，
都不能成为省略已知类别的理由。“如有要求”逐类保留条件核验，不能整组视为无需编写。
context.body_inventory为已有正文的真实标题与块号。回读后把与当前分类相关的原文标题
用outline_plan(operation="content_heading")归集到所属二三级，level1/2/3分别填标题，原题逐字保留，注明body_path、
block和归属理由；程序验证原文哈希和原章归属。素材内容不是招标强制要求，不虚构招标来源。
原一级条目、顺序、独立附件层级及有效内容均保留，新增分类只在所属原章下展开；无旧目录
时依本项目明确格式骨架组织，不套其他项目固定章名。复印件、简历等补充材料可在原附件下
展开；独立附件不能因主题相近降挂到新建“人员/方案”等容器。
子代理完成后主线程再基于真实标题逐项审查分类，不能用自己的预判代替子代理评分对齐。
保留原来源前须逐章核对其在当前registry中的真实条文与章节范围；REQ/MAND/TPL与SCORE同查。
编号存在或此前已挂接不代表语义正确，不能只补pending_sources而跳过旧引用；错标在冻结前纠正，原章节内容保留。

按第 1 步骨架的响应文件数量走两条路径之一。两条路径共用同一条铁律：来源 ID 只引用
analysis 产物里已有的 MAND/TPL/REQ/SCORE 编号，**不要自己发明编号**。每册目录树
首节点固定 `- 封面`（合册按名识别做封面页；交付形态按样例定，见 generate.md 规则
10），封面后固定 `- 目录`（合册按名识别机械生成目录页——Word 目录域+缓存清单，
不写节文件；位置与前置区语义见 generate.md 规则 11）。

**单册**（骨架只有一个响应文件）：就地补全三段：`## 目录`（树，格式见下方红线）、
`## 来源标注`、`## 目录说明`（两段格式见 annotation.md）；随后第 3 步三道清理
也在本文件就地做。

**多册**（骨架 ≥2 个响应文件）：并发派发 `tender-outline-writer` 子代理，每册一个——
在**同一条消息里一次性发出全部 task 工具调用**（subagent_type 都是
`tender-outline-writer`，多个调用必须写在同一条 assistant 消息里并行执行，
不要派一个等一个）。每个 description
第一行只写该册短名（≤16 字，如「XX 册目录编写」——过程区并发卡片靠它
区分，不要角色自述开头），第二行起必须**自带全部路径与上下文**（子代理看不到任务上下文，也不会自动加载本技能）：

- 任务目录前缀（形如 `t_ab12…/`，读写路径都要带）；
- 响应文件名 + 该册 scope 全文（从骨架原样复制，边界必须写清楚——子代理之间
  互不知晓，跨册协调全靠 scope 划分）；
- fragment 输出路径：`<任务目录>/work/outline/fragments/<册名>.md`（文件名由你派发时
  指定并保持稳定，是本技能的多册中间态）；
- work/analysis 输入文件清单（含 requirements-format / requirements-business /
  evaluation 的完整路径），并注明清理适用性：无 REQ 条目 → 该册跳过查漏补缺；
  无 SCORE 条目 → 该册跳过评分对齐；
- **来源文件名清单**（主文件 + 各补充文件的完整文件名，含扩展名——走查回原文
  核实时构造 `work/parse/<文件名>/<文件名>.outline.json` 路径的依据，从
  sources.json 取）。
- **已知要求与未读区边界**：未读区只限制依赖该区才能确定的未知要求；已读 REQ/SCORE
  已明确的独立实质分类，应先按所属章节规划，不能因另有未读区而整体推迟到正文阶段。
  未知区仍标待核实，不臆补其中的要求、参数或分类。
- **摘要补充**：保留原有摘要项，并列出本册「评分项／独立子维度 → 实际目录标题路径」
  的简短映射；同义标题写实际使用的标题，供主线程回读 fragment 核实。
- **原有结构与内容**：生成或覆盖骨架前，先读取已有目录（如有），派发时附上本册原一级
  条目、顺序、独立附件层级及有效内容与来源的保留要求；招标文件明确格式优先，新增分类只在
  所属原章节下补 L2/L3。无已有目录时依本项目明确骨架组织；未规定的按本项目语义规划，
  不套用其他项目章节。

子代理在 fragment 里完成「R2 三段 + 三道清理」（规则同第 3 步表格的 references），
返回简短摘要（节点数/来源标注数/跳过声明/待澄清项）。派发后主线程只等待与汇总，
**不要自己写目录**（初稿与清理都是子代理的活）。

### 第 3 步：三道清理（单册路径就地修订；多册路径已在子代理内完成）

| 道 | reference | 输入 | 跳过条件 |
|---|---|---|---|
| ① 查漏补缺 | revise-gapfill.md | 目录 + requirements-business 的 REQ 清单 | 无 REQ 条目 |
| ② 评分对齐 | revise-scoring.md | 目录 + evaluation 的 SCORE 清单 | 无 SCORE 条目 |
| ③ 走查定稿 | revise-walkthrough.md | 目录 + 全部来源（需核实的回原文，先读 outline 定位） | 无 |

顺序固定 ①→②→③；跳过某道时向用户声明（如「已跳过评分对齐：无评分条目」——
多册路径的跳过声明由子代理摘要带回，汇总时转达用户）。
每道造成的新增/删除/改名节点，**同步更新** `## 来源标注` 与 `## 目录说明`：
新增节点立即补标注（无来源的过渡章在来源标注中不写该行）；删除的节点移除其标注行。

### 第 4 步：合并 fragments（多册路径）

全部子代理返回后：

合并前，主线程读取已有 `work/analysis/evaluation.md` 与各册实际 fragment 的 `## 目录`，
按 `revise-scoring.md` 逐项核对本册评分项及其独立实质子维度是否有对应的实际标题路径；
不能仅凭摘要、来源 ID 挂接或节点概述判定已覆盖。缺失时按下方第 3 条只重派对应册补足
缺项，其余册不动；回读修正后的 fragment 核实通过，再继续合并。
同时以本项目格式要求及已有目录（如有）为准，核实原一级条目、顺序、独立附件层级、
原有有效内容及来源标注均保留；错标须回读本项目依据核实后更正。新增分类只在所属章节
下展开。拆章、降挂、漏项或有效来源丢失，
同样只重派对应册修正。
尤其复核复用节点的全部来源：标题相似、评分已覆盖或来源编号合法均不足以证明对应条文正确。
发现旧需求/模板/评分错挂时，先重派核正实际子稿，再用replace_source核正计划；不能将旧错标先冻结再要求子稿照抄。

冻结前，先 read 真实目录及facts_path中的完整评分依据。用 `outline_plan(operation="decide")` 对context.units
必审片段逐项审查，每项单独调用，unit_id/kind/reason/volume及level1/2/3直接填标量，
不传JSON字符串或嵌套数组；每轮最多6个调用、读回执再继续；独立实质类别选heading并
给出真实二三级路径，已有同义标题复用。类别中包含字段、参数或例子，不表示类别本身是参数；
有明确取值、阈值、时长、频率或具体字段的细节才按detail/proof/rubric等保留在原章。
不以“综合章已覆盖”“属于评分参数”为由省掉独立评分类别标题。缺标题先规划应补路径，
完成审查后complete冻结，再只重派受影响册落实。普通来源如需新增标题，使用context的可选
heading unit作有依据的决策；bindings不能隐式新增标题。回读registry发现旧错标，须用
operation="replace_source"清除该source_id的旧错误挂接并重给正确标题路径，原有效内容仍保留。
全部必审片段与来源归位后最后提交 `operation="complete"`，此后不能因检查失败
下调分类要求。冻结后如回读registry核实新增来源与已批准标题语义一致，可用outline_plan
用operation="bind"仅追加该册已核实来源与标题路径，保留合法细化关联；不能删/移既有来源、改分类或借此加未审标题，不能
为消除报错给不相干来源加绑定。分册编写期间的structure_only检查仅确认原结构保留，不代表评分分类已验收。
单册也在实际目录生成和三道清理后按此审查、冻结、检查。

必须调用 `check_outline` 回读真实文件检查：分类路径/来源、原节点/父级/顺序、独立附件
层级、原概述和归位理由均须保留。失败只重派被点名的册，保持冻结计划，不由主线程
改写分册；修正后再次检查。单册在三道清理后同样检查。全部通过才能合并和组装；
组装仍会重新检查实际内容，不能用旧检查结果或旧发布目录代替本轮成功。

1. 逐个 read 各 fragment，按第 1 步骨架的册序拼接——顶部 `## 项目信息`（如有）
   + 各册整段——**覆盖写** `work/outline/tender-response-docs.md`；
2. 跨册去重互查（generate.md 规则 8 的合并版）：同一实质内容只保留一个目录节点；
   确属多册必须同时出现的（如资格册与技术册都要交的身份证明类材料），在各自 scope
   注明边界；发现问题就地修订后重新覆盖写；
3. 某册失败或摘要暴露明显缺陷 → 向用户声明后**单独重派该册**子代理
   （fragment 覆盖重写），再从本步骤第 1 条重新合并，其余册不动。

### 第 5 步：组装发布

调用 **`assemble_tender`**（无参数）。检查返回：
- `悬空来源ID` → 按提示修正（多为编号拼写或清单行序漂移）后**重新组装**；
- `不符合列表格式的行` / `未挂到任何目录节点` 警告 → 目录树有行被跳过或标注
  标题与树对不上（丢节点），按提示修正后**重新组装**；
- `未被任何目录节点引用的来源ID` → 逐条判断：能归位的修订目录**重新组装**；
  确属无需对应章节的（如扣分项、后续轮次才出现的最终报价表）**必须在最终回复
  点名列出**并各给一句处置建议，不得只字不提；
- `[组装发布成功]` → `update_task_progress` 更新进度，告知用户投标目录已生成、
  可在界面打开查看（后续正文阶段经 read_artifact 消费当前目录）。

## 树格式红线（assemble 的解析协议）

- 每个章节一行，以 `- ` 开头（Markdown 无序列表）；
- **无编号**：禁止「第一章」「1.」「1.1」「(1)」等前缀（可保留「附件X/表X」
  标注）——章节编号由合册工具按树序自动生成（格式在目录产物里可配），树节点
  自带编号会双重编号；
- 真实缩进表达层级：每级 2 空格（L1 顶格、L2 缩 2、L3 缩 4）；
- 独立附件号/表号条目彼此**平级**，严禁互相嵌套；
- 目录树不用代码块包裹。

违反红线（如带编号前缀的行）**不会被解析进树**——组装器会跳过该行并在返回中
⚠️ 警告（来源标注同时会对不上号）；看到此类警告须修正后重新组装。

## 路由规则

- **全量重生成**：从 R1 重来（覆盖写 tender-response-docs.md）。
- **单道重跑**：「再走查一遍」「重新做评分对齐」→ 只执行对应道（读当前 `## 目录` →
  按该道 reference 修订 → assemble）。
- **单册重做**（多册场景）：重派该册的 `tender-outline-writer` 子代理（fragment
  覆盖重写）→ 重新合并 → assemble；其余册不动。
- **目录说明单独修订**：只改 `## 目录说明` → assemble。
